# Incomplete synthetic revision prototype — NEVER DEPLOY

This is an **unwired unit-level prototype**, not the requested dashboard experiment. Do not use with real data, identities, or an existing database. The existing actual-ui fixture remains unchanged and has no revision support.

`revision.py` sketches a transaction-scoped authorization path: the bank mutation, idempotency ownership and revision update share the same SQLite transaction; the snapshot reads bank state and revision in one transaction. Only gift, save and spend are modeled. Setup installs the marker only on an empty, explicitly bootstrapped synthetic family; the marker is not a migration. Unit tests compare the full SQLite catalog and all table rows on rollback. The mutation path assumes every subsequent mutation exclusively uses this wrapper. This is **not enforced** by a Durable Object or gateway: direct FamilyAuthorization or FamilyBank mutations bypass revision. Synthetic bootstrap creates a kid through the old API before the fixture is exposed. Those limitations make the prototype unsafe to wire in as-is.

Not implemented or verified: real Durable Object runtime integration and transaction semantics for this revision path, cross-family socket authorization, post-commit revision notifications and dropped-push recovery, dashboard revision ordering and delayed snapshots, reconnect/backoff and timer cleanup, safety reconciliation, concurrent commit tests, and the required two-Chromium end-to-end fault matrix. The fixture has no production identity, authentication, hibernation or durability claim. Do not deploy or treat unit tests as evidence of hosted reliability.

Before continuing, build a separate DO fixture whose complete mutation surface is constrained to the transaction-scoped path; prove schema/bootstrap invariants, rollback and concurrent commits in genuine workerd; then implement and test the browser state machine and independent driver. There is no safe automatic migration path here.
