# Synthetic revision backend prototype — NEVER DEPLOY

This is a disposable local experiment, not a production service. Never use real data or identities. There is no migration for an existing database.

`revision.py` initializes the complete supported schema and revision marker together only on an empty database. Its authorized transaction commits the real bank mutation, operation ownership and per-family revision together; snapshots read bank state and revision in one transaction. It supports all seven synthetic bank actions (add_kid, gift, save, withdraw, spend, invest, collect_rewards); setup creates the initial child through the same revision path. Replays, business failures, and domain no-ops do not advance the revision, even if operation bookkeeping is recorded. Domain rows are compared inside the transaction, so collecting a matured zero-gain bond advances it despite returning zero. A fixed catalog digest and marker checks reject unsupported schemas, including additions; changing the schema requires an explicit new version. This is not a row-integrity or physical-index check.

The local actual-ui Durable Object uses composition rather than inheriting the raw public `FamilyBank.mutate` RPC. Its sole bank mutation entry points use the revision wrapper. After commit it sends `{type: "invalidate", revision: N}` only to currently authorized sockets in that family. Fake grants, driver controls and privileged setup are local test machinery, not a security design. Arbitrary trusted Python with direct storage access can bypass the wrapper; it is not a sandbox.

Run `python spike/sync-revision/test_runtime.py` with the pinned `tests_hosted` Wrangler dependencies installed. It creates isolated loopback workers and synthetic state, exercises real mixed-language DO RPC and sockets, rollback, retry, concurrent same-ID calls, schema rejection, revocation and family isolation, then restarts Wrangler and verifies persistence. Its disposable test-only subclass uses explicit SQL to mature a synthetic bond and force its payout equal to principal; this bypasses revision solely to arrange the zero-gain test and is not an application mutation endpoint. It deletes its temporary source and state. `python -m unittest discover -s tests_hosted -p 'test*.py'` runs the backend unit suite.

The actual-UI synthetic client now handles revision-bearing invalidations; see `../actual-ui/README.md` for its browser tests and limitations.

**Durable-write revision only:** equal revision does not imply equal pending interest, allowance, bond readiness, or other time-derived state. The synthetic client accepts fresh equal-revision snapshots ordered by request time, retains 1-second animations, and reconciles periodically.

There is no durable notification outbox, real identity, production auth, hibernation, crash durability or deployment. Notifications can be lost after commit. Local runtime and graceful restart tests are not proof of hosted reliability.

The bounded fingerprint compares full rows of kids, bonds, transactions, and history before and after each supported mutation; this can be expensive at the hosted row limits. Settings are not fingerprinted because none of the seven permitted mutations changes them. Adding a setting-changing action would require revising this contract; in particular changing the durable `time_offset` setting must not be described as an unrevisioned passage of time. The runtime test instead advances the shared in-memory, test-only per-object read clock, restores the global function after the synchronous read, and checks identical full storage and revision alongside changed pending interest. It does not expose a production clock control; client reconciliation is separately tested by the actual-UI browser suite.
