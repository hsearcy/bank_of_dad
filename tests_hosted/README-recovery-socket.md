# Synthetic recovery + revision socket bridge — NEVER DEPLOY

`synthetic_recovery_socket.py` is a separate v3 fixture, not a dashboard or production service. It composes `RecoveryRevisionAuthorization`, exposes only protected `snapshot`, `mutate`, `pending`, `outcome`, `acknowledge` and an authenticated socket, and never exposes a raw/v1 bank RPC. Its `fixture_*` controls and `synthetic_recovery_socket_caller.js` are deliberately **unauthenticated and privileged**, including bootstrap, grants, revocation, expiry, and injected faults. The driver must remain isolated on loopback, never be deployed, and never receive real identities, credentials, or data. Fake tokens appear in URLs. Socket authorization is the synthetic family-local grant, not real browser identity or a secure gateway.

A new operation creates pending recovery even if its business result is false or its domain effect is a no-op. The fixture sends exactly one generic `{"type":"invalidate"}` after that transaction commits, and after the first committed acknowledgment; it sends no duplicate on replay or repeated acknowledgment and none on rollback. Domain changes are included in the same generic notification; the existing domain revision is not advanced for pending-only transitions. A client must refetch both authorized snapshot and pending state even if revision is unchanged. Frames contain no operation ID, actor, payload, result, family or revision. Before each send, the fixture rechecks that socket's current family and grant without an intervening await; denied sockets are closed on the next same-family fanout. All currently authorized sockets in the same family receive every invalidation, including those for a different principal's private pending record. **This leaks the timing and occurrence of activity within that family**, even though its contents remain protected; it is not an acceptable privacy policy without explicit review. No other family is notified. This choice is synthetic, not a production design decision.

Run `python tests_hosted/recovery_socket_integration.py` with the pinned Wrangler installed in `tests_hosted` (`npm ci`) and Node with native WebSocket support. It creates isolated temporary sources, storage, processes and loopback ports, using fake data. The privileged test driver snapshots all SQLite catalog entries and tables (including sequences), tagging each value with its SQLite type. Tests compare the full snapshot on rollback, denial and replay, and assert the exact inserted idempotency, ownership and pending rows on first false/no-op results, with every preexisting row unchanged. Event-triggered reads observe committed bank and pending state, including a null pending result after acknowledgment. The fixture calls `_notify` only after the synchronous transaction returns; that code order and local observation support event-after-commit, but event-triggered reads alone cannot prove the event was not premature under Durable Object scheduling, nor establish crash behavior. A test-only injected send-path exception verifies committed bank and recovery results, including the acknowledged outcome and duplicate-free retries after a graceful restart; this simulates a send failure, not a real transport outage. Revoked and expired clients must actually observe close events after a same-family fanout; no particular close code is guaranteed across runtimes or networks. Other checks cover two principals and families, exact frames, concurrent retries, specific denial/fault categories, and graceful restart. Negative event assertions use bounded 120 ms quiet windows and do not prove indefinite absence. A real HTTP client closes after a test gate observes the completed DO RPC; the gateway then resumes its response. This does not prove the gateway noticed the disconnect, an upstream RPC response loss, a crash, or durable notification delivery.

Notifications are best effort, not a transactional outbox: a crash between commit and fanout or socket/network loss can miss an event. Reconnect/resume and bounded reconciliation must refetch authoritative state in a future client. Ordinary sockets pin the object; hibernation, scale, real identity, origin/session protection, production security, trusted clock/rollback, backup restoration and migration remain unresolved. The actual dashboard and its recovery UI remain unwired and unchanged; this test does not validate any UI or deployed service.
