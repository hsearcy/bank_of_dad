# Synthetic operation recovery core (not a gateway)

`RecoveryAuthorization` is an internal, synchronous, experimental core for **fresh v2 families only**, not wired to `FamilyBank`, HTTP, or the UI. V1 and v2 authorization catalog checks reject each other's schemas. Bootstrap requires an empty database. There is no migration or in-place upgrade, and no data should be migrated until an independently reviewed, tested migration preserves all historical operation ownership and establishes a safe initial acknowledgment state. Self-host and the existing hosted API are unchanged.

After trusted family routing and verified identity provisioning, every recovery call rechecks the local grant, membership, role, expiry, and family in the same transaction. A new ID records the normalized request, exact JSON result, issuer/subject ownership and unacknowledged state atomically with the bank mutation. A database unique index enforces one pending result per principal per family. Pending discovery and exact-ID lookup are principal-scoped. Same-ID retries return the stored result, including business failures; changed payload or another principal is rejected. Acknowledgment requires the exact operation ID and JSON result, is repeatable, and does not acknowledge an unknown operation. Once acknowledged, an old ID still returns its original result; a different ID is allowed.

This is not an authorization boundary by itself: privileged bootstrap/grant issuance, raw `FamilyService`, database access and a legacy or alternate mutation path must never be exposed to clients or usable for the same family. A production gateway would need verified identity, trusted family routing, safe serialization/error handling, bounded inputs, CSRF/session protection, and an authenticated explicit review/ack UI. It must route *all* family writes through this protocol. No external network occurs inside the transaction. The browser must discover and display the pending request and result before allowing acknowledgement; a click must correspond to the exact displayed result, not an automatic ack after a response.

## Limits and verification

- **Clock rollback is unresolved:** grant expiry relies on a trusted nondecreasing wall clock. A grant accepted at 1009, rejected as expired at 1010, is accepted again at 1009, including after recreating the authorization object. The regression test records this unsafe behavior; it is not rollback protection. A naive high-water update inside the authorization transaction is rolled back on denial or later faults. A safe design needs separately durable observed-time recording, serialization with authorization and privileged grant issuance, and tested failure/restart/concurrency semantics. No such mechanism or schema migration is provided. Even a persisted high-water cannot detect elapsed time never observed, a lying clock at cold start, or restoration of an older backup. Do not use this core where reliable expiry is required.
- Acknowledgment is an intentional semantic boundary. After it, the server cannot infer whether a new ID represents a new human intention or a stale duplicate. Do not claim exactly-once human intent.
- Rows are retained indefinitely. Safe retention, capacity limits, backup rollback/replay policy, principal migration, account recovery and permanently revoked principals need product and security design. Restoring an older snapshot may lose a committed operation and cannot provide exactly-once protection across rollback.
- Existing adapter INSERT-on-conflict rowid checking can reject a membership update on a newly restored SQLite connection until a successful insert has occurred. This fails closed but is an availability limitation, not solved here.
- SQLite harness tests use actual bank/auth functions and durable database backup/restore. Its concurrency uses a lock around `transactionSync`: this is a model, not controlled contention inside a local DO. The concurrent local Wrangler smoke accepts either serialized action/ack order and does not force both interleavings. A separate disposable local Wrangler smoke exercises Python RelayDO → RecoveryDO RPC, restart persistence, grant rotation, concurrent acknowledgment/action, and an injected post-record rollback. Another local-only fixture exercises actual JS Worker → Python recovery DO RPC with native JSON values, errors, rollback, and actual `FamilyBank.read` rejecting v2 while recovery rejects v1. Run `PYTHONPATH=.:tests_hosted python tests_hosted/js_recovery_integration.py` and `PYTHONPATH=.:tests_hosted python tests_hosted/recovery_integration.py` with the pinned Wrangler installed or `WRANGLER_BIN` set. These intentionally unauthenticated fixtures must never be deployed. They do not prove deployed runtime, real identity, production gateway, browser review, production data, or push; the separate synthetic UI remains read-only and all-write integration does not exist.
- SQLite state is trusted; corruption/tampering, arbitrary privileged writes, compromised server components and rollback to earlier backups are outside the guarantee. Keep the synthetic core isolated until the migration, integration, security, and runtime gaps are addressed.
